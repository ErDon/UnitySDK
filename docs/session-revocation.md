# 游戏会话撤销

服务端新增 `POST /v1/session/revoke-all`：使当前账号在指定游戏、应用、环境、平台绑定下的全部游戏会话失效，包含调用者自己的会话。微信、抖音、TikTok 的配置化服务均提供此路由；不需要新增密钥。

这项操作只处理本 SDK 的游戏会话，不调用平台 OAuth 撤销、不删除平台访问/刷新令牌、不封禁账号，也不取消支付或退款。另一个接口已提供 [TikTok 平台撤销联动](tiktok-revocation.md)，两者不能混用。`SDK.CancelLogin` 则只取消本地等待，不能代替服务端会话撤销。

## HTTP 接入

发送到自己的 HTTPS 游戏后端：

```http
POST /v1/session/revoke-all
Authorization: Bearer <游戏会话>
Content-Type: application/json

{"gameId":"game","appId":"app","environment":"test","platform":"TikTok"}
```

成功响应：

```json
{"revoked":true,"scope":"game-sessions","callId":"server-generated-id"}
```

主体身份仅从 Bearer 会话读取，正文中的 `subject`、用户 ID 或其他会话字段不能指定要撤销的账号。其他游戏、环境、平台、应用及其他账号不受影响。请求沿用登录路由的限流和 8 KiB 正文上限；不接受 URL 查询参数中的会话。日志包含接口 `Session.RevokeAll`、时间、关联 ID、唯一日志 ID 与脱敏参数，不记录会话内容。

收到成功后，上层应停止使用旧会话并清理自己的登录状态；本 SDK 尚无专门的 Unity `RevokeAll` 聚合入口，可由游戏的后端请求层调用。若游戏退出业务需要彻底重置 SDK，可以再调用现有 `UnitySdkHost.Shutdown()`。用户随后主动获取新的平台 code 并登录仍可签发新游戏会话。

重复使用已撤销会话调用本接口会返回 `401 AUTH.SESSION_INVALID`，不是幂等成功响应。若第一次请求响应丢失，不能凭重试的 401 证明平台授权已经撤销；本接口本来就不撤销平台授权。

| 错误 | 含义 |
| --- | --- |
| AUTH.SESSION_INVALID / 401 | 会话缺失、过期、已撤销，或不属于请求绑定 |
| AUTH.APP_NOT_ALLOWED / 403 | 服务端未配置这个游戏/应用/环境/平台绑定 |
| REQUEST.INVALID / 400 | 正文或绑定字段无效 |
| AUTH.LOGIN_REVOKED / 409 | 此错误在登录兑换返回：登录开始后该账号会话被撤销，拒绝迟到签发 |
| AUTH.RATE_LIMITED / 429 | 请求被限流；按 Retry-After 延迟 |
| SERVER.CAPACITY / 503 | 会话或撤销记录容量达到限制，操作未完成 |
| SERVER.STORAGE_UNAVAILABLE / 503 | 存储失败，不能报告撤销成功 |

## 并发与存储契约

登录在请求平台前读取存储的全局撤销序号。撤销事务递增序号、记录绑定和账号的撤销版本，并删除全部匹配会话。签发会话时，在同一写事务中检查该账号是否在登录开始后被撤销；若是则返回 `AUTH.LOGIN_REVOKED`。其他账号或绑定的撤销不影响这个登录。

因此已经开始但尚未签发的旧登录无法恢复会话。已经通过认证并开始执行的业务请求不会被强行回滚；需要强撤销语义的业务应在提交敏感操作前重新认证。平台令牌可能仍由登录验证器保存，本地会话撤销不意味着平台令牌删除。

自定义服务端存储须支持：

- `sessionRevision()`：返回非负安全整数撤销序号。
- `putSession(hash, record, revision)`：原子比较账号撤销版本并写入；不能忽略第三个参数。
- `revokeSubject(bindingKey, subject)`：在同一事务中递增版本、更新撤销记录、删除匹配会话。

MemoryAuthStore 仅适合测试，重启后状态丢失。SqliteAuthStore 可在同一机器的多个连接间保证上述事务语义；不是跨机器数据库。

## SQLite v1 → v2 升级

本轮将认证库 schema 升为 2，新增撤销表、全局序号表和账号索引，保留已有会话与 code 防重放记录。首次打开 v1 认证库时自动在事务中迁移；不支持的 schema 仍被拒绝。

部署前停止并排空所有旧服务实例，备份认证库，然后统一升级；不要让已经打开 v1 数据库的旧进程继续写入。旧代码不理解新撤销契约，不能混跑，也不能直接降级读取 v2。若需要回滚，应使用停机时的完整备份并评估会话恢复风险。

撤销记录目前保留至数据库维护，不按时间自动删除，以免极晚返回的登录绕过撤销。不同账号记录数受存储 `capacity` 限制；SQLite 默认 100000。达到上限时新账号撤销会整体失败并返回 SERVER.CAPACITY，原会话不会被部分删除。生产部署需监控容量并规划维护，不能直接在线清空撤销表或重置序号。

## 本轮验证

- [x] 内存及 SQLite 的同账号多会话、跨游戏/环境/账号隔离。
- [x] 撤销与迟到登录竞争，其他账号仍可签发。
- [x] 双 SQLite 连接的旧版本提交拒绝、重启后保持失效。
- [x] v1 迁移保留会话与防重放记录，容量失败事务回滚。
- [x] 三平台配置服务 HTTP 路由、认证与日志脱敏。
- [x] Unity 对 AUTH.LOGIN_REVOKED 的原因与重试策略映射。
- [x] TikTok 独立撤销接口已接通平台请求、凭据删除、会话失效和受控恢复，见上述专项文档；真实平台及不确定结果核查仍待验收。

本轮没有请求真实平台授权撤销，也没有注销任何用户账号。
